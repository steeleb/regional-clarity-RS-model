Regional Clarity RS Model · LS8 Harmonization

What happens when the cross-sensor reference moves from Landsat 7 to Landsat 8

Every prior version of this pipeline harmonizes cross-sensor reflectance to an LS7 reference, using Gardner et al.'s per-band quadratic coefficients. This project asks two questions from one shared setup: what changes if that reference becomes LS8 instead, and can a usable algorithm be built from Landsat 8/9 alone, with no cross-sensor correction at all? A fresh 5-seed HUC8-random ensemble (the same architecture as workflow v3) was rebuilt from scratch for both questions, sharing one base dataset so the comparison is genuinely controlled rather than confounded by different rows or splits.

What this project tests

Two related questions, one shared setup

Cross-sensor harmonization exists because Landsat's optical instruments changed generation between missions - ETM+ (Landsat 7) and OLI (Landsat 8/9) have different relative spectral response curves, so the same water body produces slightly different raw reflectance depending on which satellite happened to pass over. Every earlier report in this project harmonized everything to an LS7 reference, inherited from the upstream AquaMatch compile step without ever being tested against the alternative. Two questions follow directly:

  • Does referencing to LS8 instead of LS7 change model accuracy? OLI is the more modern instrument, with narrower, more distinct spectral bands than ETM+ - referencing to it could plausibly preserve more of that specificity than collapsing everything down to ETM+'s coarser response.
  • Is there enough Landsat 8/9 data alone to build a usable algorithm, with no cross-sensor correction step at all? If OLI/OLI-2 data alone can carry a model, an entire source of harmonization error and complexity disappears for any future deployment that doesn't need the older missions' longer time series.

Both questions are answered from one shared base dataset (see below), so the comparisons are genuinely controlled rather than confounded by different rows, different splits, or different sample sizes doing the work instead of the thing actually being tested.

Data

LT04/LT05 have nowhere to go under an LS8 reference

The upstream coefficient table (Gardner et al.'s per-band quadratic cross-sensor corrections) contains exactly two correction families referenced to LS7 (from LS5 and from LS8), used by every prior report in this project - and exactly one referenced to LS8 (from LS7 only). There is no LS5→LS8 or LS4→LS8 coefficient anywhere in the table, upstream or otherwise. That is a real constraint, not a processing choice: Landsat 4 and 5's Thematic Mapper instrument was never directly cross-calibrated against Landsat 8/9's OLI in the coefficient set this project depends on.

This is exactly the trade-off anticipated going in: losing Landsat 4/5's matchups in exchange for whatever specificity an LS8 reference buys. The rest of this report measures whether that trade is worth it, and separately, what a corpus restricted even further - to only the sensors (LC08/LC09) that need no cross-sensor correction at all - can support on its own.

Method

One base corpus, three arms

A single R script builds one 7,112-row base dataset restricted to mission %in% c("LE07","LC08","LC09"), carrying both the existing LS7-referenced bands (*_corr7, joined straight across from the existing modeling dataset for these same rows) and newly-computed LS8-referenced bands (*_corr8, via the existing sat_to=="LS8" Gardner coefficients - LC08/LC09 pass through unchanged since they're already the target sensor, verified bit-for-bit; LE07 is transformed). A fresh 5-seed HUC8-random ensemble (identical architecture to workflow v3: one fixed holdout no ensemble member trains on, 5 independent 4-fold CV arrangements for the rest) was built from scratch on this corpus's own HUC8 distribution - v3's holdout seed left Lake Powell (HUC4 1407) at 0% holdout representation on this smaller corpus, so seeds 1-30 were swept directly and seed 12 adopted (holdout shares: overall 19.7%, HUC4 1407 19.8%, HUC4 1701 14.6% - all close to each other).

Three arms share this exact setup, varying exactly one factor each:

  • Arm A (LS7-ref, control): same 7,112-row corpus, same splits, the existing LS7-referenced bands. The true baseline for isolating the reference-switch effect.
  • Arm B (LS8-ref): identical rows and splits to Arm A, the newly-computed LS8-referenced bands instead. The only thing that differs from Arm A is which reference the raw bands are expressed in.
  • Arm C (LS8/9-only): a strict row subset of Arm B - mission %in% c("LC08","LC09") only, 1,925 rows - using the same LS8-referenced bands (which for these two missions are simply the raw, uncorrected bands, since no cross-sensor transform applies to a sensor being referenced to itself).

Each arm ran its own independent full pipeline per seed: gap-aware feature-group comparison (optical / +site / +weather / +site+weather), correlation pruning, backward elimination (xgboost, lightgbm, and joint), gap-aware final tuning, and final 4-fold training - unweighted throughout, following the recipe workflow v3 adopted. All 15 seed-runs (5 seeds × 3 arms) were smoke-tested at reduced trial counts before the full run, and completed cleanly.

Comparison 1

Does LS8-referencing actually help?

Arms A and B share every row and every split - the only thing that differs is which reference the optical bands are expressed in before feature engineering runs. That makes this the cleanest possible test of the reference-switch question alone.

The improvement is real but modest in aggregate. It's more interesting broken out by basin:

10 of 13 basins improve under the LS8 reference, most by a modest 1-8%. Lake Powell (HUC4 1407) improves the most of any basin (RMSE 3.992m → 3.799m, −4.8%) - a large reservoir where a more modern instrument's spectral specificity plausibly matters more, given its already-known status as an extrapolation-heavy basin (see the SHAP finding in workflow v3's report). HUC4 1701 is one of only two basins that get worse (2.237m → 2.308m, +3.2%) - consistent with that basin's difficulty tracing to a genuinely weak, low-magnitude optical signal in naturally clear water rather than a fixable cross-sensor artifact, the same conclusion workflow v3 reached about it. HUC4 1704 is the other basin that worsens, and more sharply in relative terms (+15%, though n=19 is small enough that this could be noise) - notably sharing the same "170X" HUC4-prefix region as 1701, which may or may not be coincidental.

Result

Switching the cross-sensor reference from LS7 to LS8 is a real, controlled improvement on this shared 3-sensor corpus: −1.4% RMSE and +0.018 R² overall, driven by broad small gains across most basins and a genuinely large gain at Lake Powell specifically. It is not a universal win - HUC4 1701 (and, more weakly, 1704) get modestly worse - consistent with those basins' difficulty being about a weak optical signal rather than which reference sensor the bands are expressed in.

Comparison 1, continued

What changes in feature selection

Backward elimination was run independently for both arms, across all 5 seeds and both architectures (10 independent runs per arm). The two arms don't just reach similar accuracy by similar means - which bands and indices survive elimination shifts in a way that lines up with the "more spectral specificity" hypothesis behind this whole project:

  • GR (green/red ratio) and blue_corr8 become unanimous (5/5) only under the LS8 reference. Neither the raw blue band nor this particular ratio survives elimination even once under the LS7 reference - the LS8-referenced blue band is carrying real, reliable signal that the LS7-referenced version of the same physical measurement does not.
  • NDWI and pct_forest_2006 drop out of unanimous status under the LS8 reference (5/5 under LS7-ref, down to partial under LS8-ref) - not necessarily lost information, plausibly redundant with whatever GR and blue_corr8 now carry instead.
  • shore_flag stays a strong but not perfect performer either way (4/5 under LS7-ref, 3/5 under LS8-ref) - the small drop is within the range already seen for boundary features in this project, not a meaningful regression.
  • The three top-ranked optical ratios in workflow v3's SHAP analysis - BG, BR, and effectively green_corr7/green_corr8 - are unanimous in both arms, unaffected by which reference sensor is used. The reference switch adds information at the margin; it doesn't change what the model leans on most.

This is direct evidence for the "gain in spectral specificity" half of the motivating question: an LS8 reference doesn't just shuffle which of two redundant features survives pruning (the way, for example, red_corr7/green_corr7 traded off in workflow v3's gap-aware comparison) - it makes a previously-uninformative band and ratio reliably useful.

Comparison 2

Can Landsat 8/9 alone carry an algorithm?

Arm C strips Arm B down to only the rows that need no cross-sensor correction at all - LC08 and LC09 are already the reference sensor, so their bands are used exactly as measured. At 1,925 rows total (211 in the holdout), this is a real test of whether a much smaller, mechanically simpler corpus can still support a usable model.

RMSE looks worse and the ensemble under-predicts on average - but MAE and R² are actually better than the full-corpus arm, an unusual combination that's explained entirely by composition, not model quality:

Lake Powell (HUC4 1407) and HUC4 1701 - the two hardest basins in this entire project - make up 55 of Arm C's 211 holdout rows (26%), against 151 of 1,114 (14%) in the full-corpus arms: with fewer alternate-sensor matchups to dilute them, the two hardest basins are structurally over-represented in the smaller holdout. On a basin-matched basis, Lake Powell does about as well under LS8/9-only as under the full corpus (3.540m vs. 3.799m) despite 73% less training data; HUC4 1701 is genuinely worse (2.731m vs. 2.308m); the three easier basins (1602, 1406, 1019) are comparable or better. The aggregate RMSE going up is a real fact about this smaller holdout's composition, not evidence the model itself is worse.

The one place LS8/9-only shows a genuine cost, not just a composition effect: feature-selection stability. Across the 5 seeds, Arm C's intersection-of-per-model feature set ranged from 15 to 24 features (vs. 19-21 for the full-corpus arms), with only 12 features unanimous across all 5 seeds, against 16-17 for Arms A and B. Several features that were rock-solid at the full corpus's sample size - NR, nir_corr8, blue_corr8, GR, swir2_corr8 - become boundary cases (3-4 of 5 seeds) here. This is an honest small-sample-selection-noise finding: at ~1,925 rows, exactly which features backward elimination keeps depends measurably more on which rows happen to land in which fold.

Result

Yes - a real algorithm comes out of Landsat 8/9 data alone, and its typical-case accuracy (MAE, R²) is comparable to or better than the full multi-sensor corpus, including on the hardest basin (Lake Powell) specifically, despite 73% less training data. The apparent RMSE regression is a holdout-composition artifact, not a modeling one. The real, measurable cost is feature-selection noise: with a third the training rows, which features survive elimination becomes noticeably less reproducible across independent seeds, even though the resulting models still perform well.

Conclusion

Both questions have a clear answer

Switching the reference to LS8 is a real, modest, controlled improvement - not a wash, and not confounded by the sensor drop it requires, since Arms A and B share every row. It helps most basins a little and Lake Powell a lot, at the cost of HUC4 1701 (and mildly, 1704) getting slightly worse - and it does so partly by making previously marginal spectral information (the raw blue band, the green/red ratio) reliably useful, exactly the "spectral specificity" mechanism motivating the question. That improvement comes bundled with a real, unavoidable cost: LT04 and LT05 (44% of the full corpus) have no path to an LS8 reference under the coefficient table this project depends on.

A Landsat 8/9-only algorithm is genuinely viable, not merely possible in principle - typical-case accuracy holds up, including at the hardest basin in this whole project, on a corpus 73% smaller than the full multi-sensor one. The trade is feature-selection stability, not accuracy: exactly which features get selected is measurably noisier at this sample size, which matters more for interpretability and reproducibility across future re-runs than for any single model's holdout performance.

Recommendation

If the L4/L5 time series isn't needed for a given deployment, an LS8-referenced, LE07+LC08+LC09 corpus is a strict improvement over the current LS7-referenced production recipe on the same data, and should be adopted for any workflow that doesn't require the longer historical record. An LS8/9-only corpus is a credible option specifically where simplicity (no cross-sensor correction step at all) matters more than feature-selection reproducibility - most useful for a forward-looking deployment that doesn't need to explain historical Landsat 4/5/7 observations at all. Neither result changes the standing recommendation to keep ensembling across multiple independent splits (per workflow v3) rather than trusting any single split's feature-selection outcome, especially for the smaller LS8/9-only corpus where that protection matters most.

A specific follow-up was flagged during this project rather than started here: whether the original outlier-HUC investigation's findings (Lake Powell and the HUC 1701 cluster's compression bias) should be re-examined on this narrower, LS8-referenced or LS8/9-only sensor set rather than the full LS4-9 corpus it was originally diagnosed on - deferred pending further direction, since this report's own basin-level results already show both basins behave somewhat differently under these narrower corpora.
