Regional Clarity RS Model · Workflow v3

A production workflow built on an ensemble of splits, not one

Every prior version of this pipeline - the original report, the outlier-HUC investigation, and the partition-sensitivity follow-up - was built on a single, deterministic HUC4-grouped split. This workflow rebuilds the pipeline on a genuine ensemble of 5 independent HUC8-random partition assignments, evaluated against one fixed holdout no ensemble member ever trains on, and uses that same shared setup to test four things side by side: a new candidate feature (a binary shoreline/waterbody flag), whether SDD-weighted training earns its keep, whether gap-aware hyperparameter selection matters beyond the final tuning step, and whether any of this actually beats the current production configuration on equal footing.

What this workflow tests

One shared setup, four comparisons

The partition-sensitivity report showed that a single HUC4-grouped split doesn't just make final evaluation numbers hard to interpret - it reaches back into which features backward elimination keeps and what hyperparameters tuning selects. A follow-up spot check (2 alternate schemes) found two features, swir1_corr7 and tmax_degC_prev30, that production's single-split elimination dropped but every alternate-scheme rerun kept. That was enough evidence to warrant a real fix: an actual ensemble of independently-run selection pipelines, not a two-scheme sanity check.

Rather than run each open question as its own follow-on project, this workflow answers all of them from one shared experimental setup - a 5-seed HUC8-random ensemble evaluated on one fixed holdout - with two explicit head-to-head comparisons built into the design:

  • Does a new candidate feature earn a place in the model? A binary shoreline/waterbody flag (shore_flag), requested for this rebuild.
  • Does hyperparameter selection need to be gap-aware everywhere, or just at final tuning? Compared gap-aware selection against the vanilla, best-CV-RMSE-alone approach at the feature-group-comparison stage, across all 5 seeds.
  • Does SDD-weighted training earn its keep? Compared weighted (k=2.0, the scheme adopted in v1) against unweighted training, on this workflow's own final feature sets and hyperparameters.
  • Does any of this beat production? v1's frozen, currently-published feature set and hyperparameters, retrained on the same 5 splits and evaluated on the same holdout, as a controlled baseline for everything above.
Method

A fixed holdout, five independent CV-fold arrangements

Building a genuine ensemble across split assignments requires one thing the earlier partition-sensitivity rotation experiments didn't need: a test set that stays identical across every ensemble member, so no member's training ever touches it and predictions from different members can be honestly averaged together. The design:

  • Fixed holdout (3,042 rows, 24.1%): HUC8-random seed 3's partition 5, reused from the partition-sensitivity sweep - chosen because it already left a reasonable share of both problem basins in the training pool (HUC4 1701 at 37%, HUC4 1407 at 29% holdout concentration) rather than either extreme. Re-derived from scratch here and checked against the previously-published concentration numbers (43.9% / 47.0% max-partition share) as a sanity check before use.
  • 5 ensemble members (seeds 501-505): for the remaining ~80% of rows, 5 independent random-but-balanced 4-fold CV arrangements, built by reshuffling how HUC8 units distribute into folds 1-4. Each seed never sees the fixed holdout at any pipeline stage.
  • Full pipeline, per seed: feature-group comparison (optical / +site / +weather / +site+weather, each independently hyperparameter-tuned - gap-aware, per the comparison in the next section), correlation pruning, backward elimination (xgboost, lightgbm, and joint), gap-aware final tuning on the resulting intersection feature set, and final 4-fold training - all run independently per seed, so a feature or hyperparameter choice reflects that seed's own CV pool, not a shared assumption. Training is unweighted throughout, per the comparison later in this report.
  • Final production prediction: the average across all 5 seeds × 2 models × 4 folds (40 models) on the fixed holdout.

xgboost + lightgbm only throughout, per the project's established scope - the NN was excluded from every stage to avoid its process-isolation overhead across a pipeline already run 5× over. Each of the two head-to-head comparisons below (gap-aware vs. vanilla tuning; weighted vs. unweighted training) reran the relevant stage across all 5 seeds under both conditions and compared the results on the same fixed holdout.

New feature

shore_flag: a binary collapse of v2's 3-level shoreline category

An earlier side-branch (outlier_rework_v2) computed a 3-level shoreline-proximity category - 0 = open water, 1 = near-shore (within 230m, the 200m site buffer plus a 30m optical pixel), 2 = outside the matched waterbody entirely - and it actually survived backward elimination for all three architectures tested there, landing in that branch's final intersection set. It was never adopted, and its own final-evaluation numbers were mixed (modestly better test RMSE for the tree models, worse for the NN; worse CV RMSE across the board on its own split) - inconclusive enough to defer rather than decide from.

This rebuild collapses that 3-level category into a strict binary at the user's request: shore_flag = 1 if flag_wb == 1 (the site's location falls outside its matched waterbody polygon) or flag_optical_shoreline == 1 (within 230m of the matched waterbody's shoreline); 0 only when neither condition holds. Both source flags already existed per-site in the same upstream AquaMatch compile step v2 used - no new spatial work was needed, just a join and a simpler encoding. Roughly 59% of the 1,525 modeled sites (896) carry the flag - high, but plausible for lake/reservoir monitoring, where shoreline access points and boat launches are common sampling locations, not an edge case.

Comparison 1

Feature selection: gap-aware vs. vanilla tuning at the feature-group stage

Backward elimination treats the feature-group-comparison stage's chosen hyperparameters as a fixed baseline - whatever that stage picks, elimination trains with, for every step of dropping features. That stage's hyperparameter search was run two ways across all 5 seeds, to test whether it matters: vanilla (best mean CV RMSE alone, no penalty for the train-val gap - the approach used everywhere in this pipeline before) and gap-aware (pick the smallest train-val gap among trials within 2% of the best CV RMSE - the same method already used at final tuning). Everything else was held identical: same candidate pools, same correlation pruning, same elimination logic, same fixed holdout.

Correlation pruning itself doesn't depend on this choice - it only depends on which rows are in the CV pool (identical for every seed), not on how they're folded or tuned, so all 5 seeds prune the same 26-candidate pool down to the same 23 either way. One small, inconsequential swap shows up consistently: red_corr7 is pruned in favor of green_corr7 (plus BR surviving alongside it) - the two bands are highly correlated, and pruning is designed to interchange redundant features like this; it isn't a meaningful signal.

What differs is what happens during elimination itself:

  • shore_flag: 10/10 either way. Every independent elimination run - 5 seeds, 2 architectures, both tuning methods - kept it.
  • tmax_degC_prev30: 10/10 either way. Also unanimous under both tuning methods, confirming the upstream-decision spot check's flag from the partition-sensitivity work was a real signal, not a two-scheme coincidence.
  • swir1_corr7: 9/10 under vanilla tuning, 10/10 under gap-aware. The single disagreement - seed 504's xgboost run dropping it - only happens under vanilla feature-group tuning. Once that stage is also gap-aware, every seed and model agrees.
  • Everything else that varies (pct_impervious_2006, pct_cropland_2006, pct_forest_2006, elevation_m, precip_mm_prev30) flips inconsistently across seeds/models under both tuning methods, with no clear pattern - boundary noise, not a real effect either way.

Aggregate holdout accuracy is indistinguishable between the two tuning methods (within 0.001m RMSE of each other - see the full evaluation below) - gap-aware selection at this stage was never expected to move the bottom line by itself, since the fixed holdout and the already-gap-aware final tuning step do most of that work. What it buys is the consistency shown above, and a train-val gap that's now visible and quantifiable at this stage for the first time (vanilla tune() never reported one, so this stage's overfitting risk was previously invisible by construction, not merely unaddressed).

Result

Gap-aware tuning at the feature-group-comparison stage costs nothing in accuracy and buys a strictly more consistent feature-selection process: shore_flag, swir1_corr7, and tmax_degC_prev30 come out unanimous across every independent seed and model, not 9 or 10 of 10. Adopted throughout this pipeline - the train-val gap is now addressed at every hyperparameter-selection stage, not just the last one. The ~18-feature core shown above (intersection-16 plus these three) is the feature set used for everything that follows.

Neither model's hyperparameters are so unstable as to suggest the tuning process itself is unreliable - they cluster in a recognizable family each time - but lightgbm's choice is more sensitive to exactly which rows land in which fold.

Comparison 2

Does the new configuration actually beat production?

v1's originally published test RMSE (1.86m xgboost, 1.83m lightgbm) cannot be compared directly to any number in this report - it was measured on a completely different, and structurally harder, test set: v1's HUC4-grouped partition 5, which the outlier-HUC investigation showed was disproportionately composed of Lake Powell and other high-clarity, hard-to-predict water. This report's fixed holdout is a different, more moderate 24% of the data. A lower absolute RMSE here mostly reflects an easier test set, not a better model, and reporting it as a before/after improvement would be exactly the kind of split-driven illusion this whole line of work has been diagnosing.

To make a fair claim, v1's actual frozen intersection-16 feature set and frozen final hyperparameters were retrained from scratch on these same 5 CV-fold arrangements and evaluated on this same fixed holdout - holding the split and test set constant so only the feature set and hyperparameters differ between the two bars below. (v1's config trains SDD-weighted, its real published setup; the v3 ensemble here trains unweighted, per the comparison in the next section - so this comparison isolates the combined effect of the new features/hyperparameters/tuning method, not any single one of them alone.)

Does the compression bias itself improve?

The outlier-HUC investigation identified a universal high-clarity compression bias - every architecture over-predicts the clearest water and under-predicts it at the extreme end, a signature of the optical retrieval problem running out of signal, not a fixable modeling defect. Under this workflow's adopted (unweighted) configuration, that bias narrows in the well-populated low range and widens slightly at the sparse high-SDD tail relative to v1's weighted config - a pattern that has a specific, identifiable cause, covered in the weighting comparison below.

Does it help where the original investigation found the problem?

The most direct test of whether this rebuild actually fixed anything is to look at the two basins the outlier-HUC investigation named specifically: HUC4 1701 (the forested, naturally-clear glacial-lake cluster) and HUC4 1407 (Lake Powell). Both are still represented in this holdout - by design, at reduced but non-trivial concentration (37% and 29% of their respective basins' rows) - so their holdout-only RMSE is directly comparable between the two configurations.

Both basins improve, modestly: HUC4 1407 (Lake Powell) RMSE drops from 1.894m to 1.832m (−3.3%); HUC4 1701 drops from 2.067m to 2.058m (−0.4%, essentially flat). Lake Powell's larger improvement is consistent with a reservoir whose difficulty is partly about missing predictors (shore_flag, swir1_corr7, and the antecedent-temperature feature all have a physically plausible story for mattering to a large, dynamic reservoir); HUC4 1701's near-flat result is consistent with its difficulty tracing more to a genuinely weak, low-magnitude optical signal in naturally clear, low-sediment water - something feature engineering alone isn't expected to fix.

What this establishes

The outlier-HUC investigation named Lake Powell and the HUC 1701 cluster as the source of two partitions' underperformance; the partition-sensitivity work showed that was a structural, split-driven concentration problem, not a modeling failure; the upstream-decision spot check found the single split had also cut features that looked like they should matter. This controlled comparison confirms the resulting configuration helps at both named basins, and more broadly - real gains in overall accuracy and bias, concentrated somewhat more at Lake Powell than at the 1701 cluster, exactly the kind of result a feature-driven fix should produce rather than a uniform, split-driven artifact.

Comparison 3

Weighted vs. unweighted training

v1 trains SDD-weighted (k=2.0): each training row is weighted toward the high-SDD end of that fold's own range, addressing a known ceiling effect where squared-error loss is dominated by the dense low/mid-range cluster and never pushed hard on the sparse high-SDD tail. That scheme was adopted once, before this whole line of split-sensitivity work existed, and never re-tested since. Here, each seed's final (~18-feature, gap-aware-tuned) configuration was retrained twice - once unweighted, once SDD-weighted - and evaluated on the same fixed holdout, isolating exactly this one choice.

That widening gap holds at the fold level too: mean per-fold train-val gap grows from 0.383m unweighted to 0.429m weighted. Cross-seed agreement on holdout RMSE is about the same either way (std 0.022 unweighted vs. 0.028 weighted, both already tight). Splitting the holdout by SDD range shows why the aggregate number moves so little despite this:

Weighting is doing exactly what it's designed to do - shifting loss-function attention from the dense bulk toward the sparse, hard, high-SDD tail - and it works: top-quartile RMSE improves from 2.036m (unweighted) to 1.930m (weighted), and its under-prediction bias shrinks from −1.19m to −1.00m. But the well-populated rest of the distribution gets worse (1.034m → 1.124m), and because those rows outnumber the tail roughly 2.5:1 in this holdout, the net effect on the overall aggregate is a small regression (1.391m → 1.399m, +0.6%) alongside the widening train-val gap above.

Result: unweighted adopted, with a caveat

SDD-weighting does not clearly improve overall accuracy or fold-level reliability for this configuration - the train-val gap widens, and the aggregate holdout RMSE ticks up slightly. Unweighted training is adopted as the default production configuration on that basis. But the three-way comparison above shows weighting isn't simply worse: a weighted variant of this same ensemble is the only configuration tested that beats v1's published setup at both the bulk of the distribution and the sparse high-SDD tail simultaneously. For a deployment where tail accuracy - exactly the regime Lake Powell and the HUC 1701 cluster sit in - matters more than aggregate RMSE, SDD-weighted training on this same feature set and hyperparameters is a documented, viable alternative, not a rejected one.

Conclusion

Recommended production configuration

Four questions, one shared experimental setup: a new feature (shore_flag) earns a unanimous place in the model; gap-aware hyperparameter selection matters beyond just final tuning, at no accuracy cost; SDD-weighted training is a real trade-off rather than a clear win, so it's adopted only as a documented alternative, not the default; and the resulting configuration beats v1's frozen, currently-published setup by a real, controlled margin (−2.9% RMSE, −4.5% MAE, bias reduced from +0.142m to +0.009m) when both are evaluated on identical splits and an identical holdout.

Recommended next state

Adopt the unanimous ~18-feature core (intersection-16 plus shore_flag, swir1_corr7, and tmax_degC_prev30), gap-aware tuning at every hyperparameter-selection stage, and the 5-seed ensemble (40 models: 5 seeds × 2 architectures × 4 folds) as the production prediction mechanism, replacing the single-split final model entirely. Train unweighted by default; keep the SDD-weighted variant on hand for any use case where tail accuracy at the sparse, hard-to-predict end - Lake Powell's range, the HUC 1701 cluster's range - matters more than aggregate error. xgboost's hyperparameters are stable enough to fix at their consensus value (eta≈0.01-0.03, depth 2-4) if a simpler single-config deployment is ever preferred over the full ensemble; lightgbm's spread suggests it benefits more from staying ensembled across seeds specifically, rather than collapsed to one "representative" config.

One thing remains explicitly out of scope: the NN's role in this ensemble, excluded throughout for the same process-isolation reasons as the partition-sensitivity work. Everything else this project's backlog had flagged - split sensitivity, upstream feature/hyperparameter stability, the shoreline flag, weighting, and systemic gap-awareness - has now been tested against a shared, controlled setup, not just deferred.
