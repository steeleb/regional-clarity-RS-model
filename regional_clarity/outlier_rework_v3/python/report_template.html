Regional Clarity RS Model · Workflow v3

A production workflow built on an ensemble of splits, not one

Every prior version of this pipeline - the original report, the outlier-HUC investigation, and the partition-sensitivity follow-up - was built on a single, deterministic HUC4-grouped split. This version rebuilds the workflow top to bottom on a genuine ensemble of 5 independent HUC8-random partition assignments, each running its own full feature-group comparison, correlation pruning, backward elimination, and gap-aware hyperparameter tuning, evaluated against one fixed holdout no ensemble member ever trains on. It also formally tests a new candidate feature - a binary shoreline/waterbody-edge flag - that an earlier side-branch (v2) tried in a 3-level form but never adopted.

What this rebuild changes

From one split's decisions to a consensus across five

The partition-sensitivity report showed that a single HUC4-grouped split doesn't just make final evaluation numbers hard to interpret - it reaches back into which features backward elimination keeps and what hyperparameters tuning selects. A follow-up spot check (2 alternate schemes) found two features, swir1_corr7 and tmax_degC_prev30, that production's single-split elimination dropped but every alternate-scheme rerun kept. That was enough evidence to warrant a real fix rather than another spot check: this workflow reruns the entire feature-selection and hyperparameter-tuning pipeline independently across 5 different HUC8-random partition assignments, rather than trusting any one of them - including this one.

Two things changed at once, deliberately: the split design (HUC8-random ensemble instead of one fixed HUC4 split) and the candidate feature set (adding a new binary shoreline/waterbody flag, shore_flag, requested for this rebuild). Both needed the same full pipeline rerun regardless, so they're evaluated together here rather than as two separate projects.

Method

A fixed holdout, five independent CV-fold arrangements

Building a genuine ensemble across split assignments requires one thing the earlier partition-sensitivity rotation experiments didn't need: a test set that stays identical across every ensemble member, so no member's training ever touches it and predictions from different members can be honestly averaged together. The design:

  • Fixed holdout (3,042 rows, 24.1%): HUC8-random seed 3's partition 5, reused from the partition-sensitivity sweep - chosen because it already left a reasonable share of both problem basins in the training pool (HUC4 1701 at 37%, HUC4 1407 at 29% holdout concentration) rather than either extreme. Re-derived from scratch here and checked against the previously-published concentration numbers (43.9% / 47.0% max-partition share) as a sanity check before use.
  • 5 ensemble members (seeds 501-505): for the remaining ~80% of rows, 5 independent random-but-balanced 4-fold CV arrangements, built by reshuffling how HUC8 units distribute into folds 1-4. Each seed never sees the fixed holdout at any pipeline stage.
  • Full pipeline, per seed: feature-group comparison (optical / +site / +weather / +site+weather, each independently hyperparameter-tuned), correlation pruning, backward elimination (xgboost, lightgbm, and joint), gap-aware final tuning on the resulting intersection feature set, and final 4-fold training - all run independently per seed, so a feature or hyperparameter choice reflects that seed's own CV pool, not a shared assumption.
  • Final production prediction: the unweighted average across all 5 seeds × 2 models × 4 folds (40 models) on the fixed holdout.

xgboost + lightgbm only throughout, per the project's established scope - the NN was excluded from every stage to avoid its process-isolation overhead across what is already a 5×-larger pipeline rerun. All 5 seeds' full pipelines ran in parallel in about 28 minutes wall-clock.

New feature

shore_flag: a binary collapse of v2's 3-level shoreline category

An earlier side-branch (outlier_rework_v2) computed a 3-level shoreline-proximity category - 0 = open water, 1 = near-shore (within 230m, the 200m site buffer plus a 30m optical pixel), 2 = outside the matched waterbody entirely - and it actually survived backward elimination for all three architectures tested there, landing in that branch's final intersection set. It was never adopted, and its own final-evaluation numbers were mixed (modestly better test RMSE for the tree models, worse for the NN; worse CV RMSE across the board on its own split) - inconclusive enough to defer rather than decide from.

This rebuild collapses that 3-level category into a strict binary at the user's request: shore_flag = 1 if flag_wb == 1 (the site's location falls outside its matched waterbody polygon) or flag_optical_shoreline == 1 (within 230m of the matched waterbody's shoreline); 0 only when neither condition holds. Both source flags already existed per-site in the same upstream AquaMatch compile step v2 used - no new spatial work was needed, just a join and a simpler encoding. Roughly 59% of the 1,525 modeled sites (896) carry the flag - high, but plausible for lake/reservoir monitoring, where shoreline access points and boat launches are common sampling locations, not an edge case.

Feature selection

Does the same feature survive five independent runs?

Correlation pruning itself is stable across all 5 seeds - it depends only on which rows are in the CV pool (identical for every seed), not on how they're folded, so all 5 seeds prune the same 26-candidate pool down to the same 23. One small, inconsequential swap shows up consistently: red_corr7 is pruned in favor of green_corr7 (plus BR surviving alongside it) in every seed - the two bands are highly correlated, and pruning is designed to interchange redundant features like this; it isn't a meaningful signal.

What matters is what happens after pruning, during elimination itself - and there the result is about as clean as this kind of test gets:

  • shore_flag: 10/10. Every single independent elimination run - 5 seeds, 2 architectures each - kept it. This is as strong a consistency result as this kind of test can produce.
  • tmax_degC_prev30: 10/10. Also unanimous, confirming the upstream-decision spot check's flag from the partition-sensitivity work was a real signal, not a two-scheme coincidence.
  • swir1_corr7: 9/10. Kept everywhere except seed 504's xgboost run - still a strong, consistent result.
  • Everything else that varies (pct_impervious_2006, pct_cropland_2006, pct_forest_2006, elevation_m, precip_mm_prev30) flips inconsistently across seeds/models with no clear pattern - boundary noise, the same character as the inconsistent features flagged in the earlier spot check.
What this settles

The partition-sensitivity spot check could only say two features looked like plausible casualties of a single split. An actual 5-seed ensemble of independently-run elimination pipelines confirms it: shore_flag, swir1_corr7, and tmax_degC_prev30 all belong in the production feature set. That's a real expansion from the 16-feature intersection this pipeline has used since the backward-elimination phase - to roughly 18-21 features depending on seed, converging on a stable ~18-feature core across all 5.

xgboost's learning rate and tree depth are essentially unanimous (eta=0.01 in all 5 seeds, depth 3 in 4 of 5) - a shallow, slow-learning, moderately-regularized tree is consistently what gap-aware tuning finds best, regardless of which CV-fold arrangement it's tuned against. lightgbm shows more real spread (learning rate ranges 0.01-0.05, num_leaves mostly 7 but 15 in one seed) - consistent with the pattern already seen in the partition-sensitivity spot check, where lightgbm's hyperparameters moved less than xgboost's under one alternate scheme but not zero. Neither model's hyperparameters are so unstable as to suggest the tuning process itself is unreliable - they cluster in a recognizable family each time - but lightgbm's choice is more sensitive to exactly which rows land in which fold.

Evaluation

Evaluating the ensemble - and isolating why it's better

v1's originally published test RMSE (1.86m xgboost, 1.83m lightgbm) cannot be compared directly to any number in this report - it was measured on a completely different, and structurally harder, test set: v1's HUC4-grouped partition 5, which the outlier-HUC investigation showed was disproportionately composed of Lake Powell and other high-clarity, hard-to-predict water. This report's fixed holdout is a different, more moderate 24% of the data. A lower absolute RMSE here mostly reflects an easier test set, not a better model, and reporting it as a before/after improvement would be exactly the kind of split-driven illusion this whole line of work has been diagnosing.

To make a fair claim, v1's actual frozen intersection-16 feature set and frozen final hyperparameters were retrained from scratch on these same 5 CV-fold arrangements and evaluated on this same fixed holdout - holding the split and test set constant so only the feature set and hyperparameters differ between the two bars below.

RMSE improves from 1.432m to 1.396m (-2.5%), MAE from 1.047m to 1.024m (-2.2%), and R² from 0.627 to 0.646 - a real, controlled improvement attributable specifically to the new feature selection and hyperparameters, not to an easier test set. It's a modest effect size, consistent with adding a handful of already-marginal features rather than a wholesale architecture change - but it's a genuine one, isolated from the split-choice confound that made every earlier comparison in this project ambiguous.

Does the compression bias itself improve?

The outlier-HUC investigation identified a universal high-clarity compression bias - every architecture over-predicts the clearest water and under-predicts it at the extreme end, a signature of the optical retrieval problem running out of signal, not a fixable modeling defect. That bias is still present in v3, as expected - but it is measurably smaller at the extreme tail specifically, exactly where the new features would be expected to help if they're picking up something real about the hard basins.

Does it help where the original investigation found the problem?

The most direct test of whether this rebuild actually fixed anything is to look at the two basins the outlier-HUC investigation named specifically: HUC4 1701 (the forested, naturally-clear glacial-lake cluster) and HUC4 1407 (Lake Powell). Both are still represented in this holdout - by design, at reduced but non-trivial concentration (37% and 29% of their respective basins' rows) - so their holdout-only RMSE is directly comparable between the two configurations.

HUC4 1407 - Lake Powell - shows the largest improvement of any basin with a meaningful row count: RMSE drops from 1.894m to 1.739m, an 8.2% reduction, nearly 3× the overall ensemble's average improvement. HUC4 1701 improves too, more modestly (2.067m to 2.033m, 1.6%) - consistent with it being a harder problem to fix with feature engineering alone, since its difficulty traces more to a genuine, low-magnitude optical signal (naturally clear, low-sediment water) than to a single missing predictor. Most other basins show small improvements in the same 1-8% range; the two smallest basins (n=22, n=21) show larger relative swings that are more likely sampling noise than a real effect at that size.

The throughline closes

This is the result the whole project thread was aimed at, even if no single step guaranteed it would arrive: the outlier-HUC investigation named Lake Powell and the HUC 1701 cluster as the source of two partitions' underperformance; the partition-sensitivity work showed that was a structural, split-driven concentration problem, not a modeling failure; the upstream-decision spot check found the single split had also cut two features that looked like they should matter; and this 5-seed rebuild, evaluated on a fair, controlled holdout, shows the resulting feature set and ensemble measurably narrow the gap specifically at Lake Powell (-8.2% RMSE) and, to a lesser extent, the 1701 cluster (-1.6%) - not just on average, but where the original investigation said the problem actually was.

Conclusion

Where this leaves the production pipeline

This rebuild delivers what the partition-sensitivity report's spot check could only recommend: a feature set and hyperparameter choice validated across an actual ensemble of independently-run selection pipelines, not a single split's decision or a 2-scheme sanity check. The result is a genuine, if modest, controlled improvement (-2.5% RMSE, -2.2% MAE) over v1's frozen configuration when both are evaluated on equal footing - and three specific features (shore_flag, swir1_corr7, tmax_degC_prev30) now have strong, repeated evidence for inclusion rather than the single earlier spot check's weaker signal.

Recommended next state

Adopt the ~18-feature core validated here (intersection-16 plus shore_flag, swir1_corr7, and tmax_degC_prev30) as the new production feature set, and the 5-seed ensemble (40 models: 5 seeds × 2 architectures × 4 folds) as the production prediction mechanism, replacing the single-split final model. xgboost's hyperparameters are stable enough to fix at their consensus value (eta=0.01, depth 3) if a simpler single-config deployment is ever preferred over the full ensemble; lightgbm's spread suggests it benefits more from staying ensembled across seeds specifically, rather than collapsed to one "representative" config.

Two things remain explicitly out of scope here, both flagged in earlier reports: the NN's role in this ensemble (excluded throughout, for the same process-isolation reasons as the partition-sensitivity work), and the systemic gap-aware-tuning question for pipeline stages this rebuild also touched (feature-group comparison used the same vanilla, non-gap-aware tune() as v1/v2, consistent with existing convention, but not re-examined here).
