Part 1 · Diagnosis

RANSAC wasn't the culprit

The commit that introduced RANSAC filtering (44546c9, "apply ransac. this is too aggressive") bundled several other new QA filters into the same change, and it turned out those bundled filters — not the RANSAC steps — caused nearly all of the row-count loss.

Finding 1: the SDD-value RANSAC flag was never applied

ransac_site() computes an is_inlier column on the field-measurement (Secchi depth) side, but no chunk in 01_make_matches.Rmd ever filters on it — it's used only in diagnostic plots. It had zero effect on matchup counts before this investigation.

Finding 2: the reflectance-band RANSAC cost only ~3.4%

Comparing the current pipeline's final row count (5,199) against the same pipeline with every QA filter kept except RANSAC (5,381) isolates RANSAC's true cost: about 3.4% of rows, not 70%.

Where the other ~65% actually went

An ablation across the QA filters added in that same commit (5-day window, original full geometry QA) shows scene-level cloud cover was the single biggest cost, followed by metadata QA, with the CV/lake-type filters on the SDD side costing almost nothing:

Finding 3: geometry QA is load-bearing, not a tunable knob

A first attempt at fully removing site geometry QA (shoreline flags + single-waterbody restriction) to recover more rows caused the matching query's output to grow past 25GB within 90 seconds before being killed. Without number_int_wb == 1, one field-monitoring location can join against many ambiguously-assigned, multi-waterbody reflectance candidates — a combinatorial blowup, not a data-quality nicety. Every configuration tested after that keeps this constraint.

Part 2 · Redesign

Final outlier/QA pipeline

QA loosening alone (keeping the original full geometry QA, dropping cloud QA entirely) tops out at 6,839 rows at a 5-day window — short of the 10k floor. Widening the match window to ~16–20 days would clear it, but that was ruled out to keep match-time precision at the original 5 days. The lever that actually got there: relaxing geometry QA to just number_int_wb == 1, dropping the shoreline-proximity flags on the reasoning that near-shore contamination is already handled upstream in the siteSR remote-sensing pipeline.

  1. Region prefilter (HUC2) — unchanged, free narrowing. Nothing outside these 7 HUC2 basins can reach the final 6-state output anyway.
  2. Match window: 5 days — unchanged, explicit constraint. Not treated as a tunable lever here, even though widening it was the only way to clear 10k under the original geometry QA.
  3. Geometry QA relaxed to number_int_wb == 1 only — shoreline flags dropped. Shoreline/near-shore contamination QA already happens upstream in the siteSR pipeline; re-filtering on it here was redundant. number_int_wb is kept — it's what actually prevents the join blowup.
  4. Metadata QA unchanged (pCount ratio > 0.5, pCount > 8, per-pixel prop_clouds == 0). Cheap (~6% of geometry-only rows) and legitimate; the per-pixel cloud check here already targets contamination at the specific site.
  5. Scene cloud-cover threshold relaxed 20% → 40% — kept, not dropped. With geometry QA relaxed there's enough headroom (11,693 rows measured at 20%) to keep a real scene-level cloud filter rather than removing it.
  6. SDD-value RANSAC now actually wired up as a filter — gently: only confirmed outliers (is_inlier == FALSE) are dropped; indeterminate (too-few-observations, NA) sites are kept. Previously computed but never applied. Dropped 11,777 / 1,654,029 rows (0.71%).
  7. Reflectance-band RANSAC rebuilt as majority-vote scoring instead of winner-take-all, with missing (location, scene) lookups defaulting to "keep." The original picked the single best-fitting random iteration per site, which is sensitive to one lucky/unlucky draw. Voting across all iterations (same design as the SDD-side filter) is far more stable. Retained 96.3% of candidate rows.
Result

12,659 final training rows (region-filtered, closest-observation-deduplicated, lake/reservoir-only), up from 5,199 on the current main branch — a 143.6% increase, comfortably above the 10k floor, at the original 5-day match window.

Part 3 · Modeling

Model comparison methodology

All three models are trained and evaluated under the exact spatial holdout scheme from 03_split_data.Rmd: 5 partitions built by greedily bin-packing HUC4 basins (never splitting a basin across partitions) into roughly equal-sized groups. Partitions 1–4 form a leave-one-partition-out cross-validation loop (train on 3, validate on the 4th, rotate); partition 5 is held out entirely and touched exactly once, at the end, for final evaluation.

No-leakage discipline

Partition 5 is never used for feature selection, hyperparameter search, or model choice — only for the one final scored prediction per model. Correlation-based feature pruning is fit on partitions 1–4 only. The NN's imputation and standardization are fit per-fold on that fold's training split only, never on validation/test rows. time_diff (days between the field sample and the satellite pass) was excluded from the candidate feature set entirely — it doesn't exist at deployment time when scoring an arbitrary satellite pass with no paired field sample, so a model trained on it would learn something it can never use in production.

Feature set

58 candidate features (7 Gardner-corrected reflectance bands + 50 band-ratio/normalized-difference spectral indices, replicated from 04_make_models.Rmd, + the LaSRC/LEDAPS atmospheric-correction indicator) were reduced to 39 by correlation-cluster pruning (|r| > 0.95 connected components, keeping the feature most correlated with Secchi depth in each cluster), computed on the training/CV partitions only.

Environment note

PyTorch and XGBoost/LightGBM each bundle their own OpenMP runtime; importing both in one process segfaulted on this machine (a known macOS conda/pip packaging conflict, not a computation bug). Each model now trains in its own process, with thread counts capped to avoid the conflict entirely.

Are these models overfitting?

The headline CV numbers above are pooled across all 4 folds, which hides fold-to-fold variance. Retraining each fold individually (same tuned hyperparameters) and comparing that fold's own training RMSE to its held-out validation RMSE tells a more precise story:

Three things stand out:

  1. Partition 3 is hard for every model architecture, not just one. All three independently-tuned models show their largest train-val gap and worst R² on partition 3 (and partition 4 for the NN). If any single model were simply memorizing its training data, the hard fold would be architecture-specific; instead the same partition is hard across a shallow tree ensemble, a different shallow tree ensemble, and a neural net. That points to genuine spatial heterogeneity - partition 3's HUC4 basins likely differ systematically from the others - rather than overfitting.
  2. Partition 1 shows a negative gap for every model. Validation RMSE is lower than training RMSE on the easiest partition for all three models. Overfitting produces a positive gap by definition (worse on unseen data); a negative gap on one fold and a large positive gap on another is the signature of uneven partition difficulty, not a leaky or memorizing model.
  3. The hyperparameter search itself pushed toward simple models, which is reassuring but not a substitute for the check above. XGBoost's winning config uses max_depth=2 (3-leaf trees) with colsample_bytree=0.5; LightGBM's uses num_leaves=7 with colsample_bytree=0.5 - both are heavily regularized by construction, since a deeper/wider config would have scored worse on the CV search that selected them. The NN is the exception worth flagging: its winning config (64-64-32 hidden layers ≈ 8,800 parameters against ~7,600 training rows per fold - roughly 1 parameter per training row) has weight_decay=0 (no L2 penalty), relying on dropout (0.3) and early stopping alone. That's consistent with the NN also having the largest fold-to-fold variance (val RMSE sd=0.458, vs. 0.343 for XGBoost and 0.264 for LightGBM) and the worst held-out test performance of the three - it's the one model where "somewhat overparameterized for this dataset size" is a fair characterization, and it's the weakest performer for exactly that reason.
Bottom line

The CV-to-test RMSE gap reported in Part 4 is better explained by spatial heterogeneity across HUC4 partitions (visible consistently across all three architectures, and consistent with the HUC-1009 outlier already visible in the residuals-by-HUC4 figure) than by overfitting. LightGBM is the most stable model across folds as well as the most accurate on average - a second, independent reason to prefer it over XGBoost or the NN.

Part 4b · Refinement

Fixing the ceiling effect: SDD-weighted training

The pred-vs-observed figure above shows the same pattern flagged in the existing 04_make_models.Rmd pipeline: squared-error loss is dominated by the dense cluster of low/mid-clarity observations, so the sparse high-clarity tail is never pushed hard during training. Reusing that pipeline's fix — a per-fold training weight that scales linearly with observed Secchi depth (the highest-SDD training point counts 3× as much as the lowest, k=2) — and retraining all three models with their already-tuned hyperparameters (no re-tuning) confirms the same fix works here.

Updated recommendation

LightGBM, SDD-weighted (k=2) is the best-performing configuration found: test RMSE 1.850 m, versus 1.866 m unweighted and 1.880 m for the best XGBoost variant. It also has the smallest overall bias of any configuration (–0.043 m) and the best top-quartile RMSE among the two boosted-tree models.

Part 5 · Limitations & next steps

What to check before trusting this in production

  1. Spot-check the relaxed geometry QA on a sample of newly-admitted near-shore sites. This investigation trusted that upstream siteSR QA handles shoreline contamination; that assumption hasn't been directly verified against the new site set.
  2. The high-Secchi ceiling effect is mitigated, not solved, by SDD-weighted training (Part 4b). Weighting reduces bias substantially and improves top-quartile RMSE in all three models, but the pred-vs-observed ceiling is still visible - a bigger structural fix (e.g. a log-transformed target, quantile loss, or a two-stage model) may be worth trying if high-clarity accuracy matters most for the end use case.
  3. Investigate HUC 1009's larger residual spread specifically before deploying basin-level predictions there.
  4. Consider a real backward-elimination pass per model (as in 04_make_models.Rmd) rather than the shared 39-feature correlation-pruned set used here for a fair three-way comparison — each model may prefer a different, smaller feature subset.
  5. Re-render the tracked pipeline docs (01_make_matches.Rmd through 04_make_models.Rmd) with the new parameters once these are reviewed, since this investigation ran as standalone scripts in regional_clarity/outlier_rework/ rather than editing the Rmd pipeline in place.
